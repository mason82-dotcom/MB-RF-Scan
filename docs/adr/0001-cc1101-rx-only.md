# ADR-0001: CC1101-Empfang nur über RSSI-Abtastung (RX-only, ohne Bitdaten)

**Status:** Angenommen
**Datum:** 19.11.2026
**Entscheider:** Projektinhaber (mason82-dotcom)

## Kontext

Der RTL-SDR am Pi wird von `dump1090.service` (ADS-B) belegt. Messungen auf 433,92 MHz sind bisher nur möglich, wenn ADS-B befristet gestoppt wird. Seit 19.11.2026 ist ein CC1101-Modul an SPI1/CE0 angeschlossen (SPI0 gehört den Pironman-5-RGB-LEDs). Die SPI-Chiperkennung liefert PARTNUM `0x00` / VERSION `0x14`.

Gemessen auf dem Pi 5 am 19.11.2026:

| Größe | Wert |
|---|---|
| Ein RSSI-Statusregister-Lesezugriff aus Python (`spidev`, 2 MHz) | Median 29 µs, p99 39 µs, Max 128 µs |
| GDO0 an GPIO25 | angeschlossen (Takt-Ausgabe nach Reset sichtbar) |
| GDO2 an GPIO24 | angeschlossen vermutet (CHIP_RDYn = low) |
| `python3-gpiod` | 2.2.0 vorhanden |

Zielsignal (aus der RTL-SDR-Messreihe): 2-FSK, Töne −20,12 / +11,35 kHz um 433,920 MHz, Bursts ca. 175 ms, Paarabstand ca. 513 ms (Startpunkte).

Anforderungen:

- Burst-Metadaten (Beginn, Dauer, Pegel, Paarabstand) **parallel zu ADS-B** erfassen.
- **Niemals senden.** Kein STX, kein Schreiben in den TX-FIFO, PATABLE nur `0x00`.
- **Keine Bit-, Rahmen- oder Schlüsseldaten** erzeugen, speichern oder anzeigen. Das ist dieselbe Regel wie beim RTL-SDR-Monitor, der nur Metadaten in SQLite ablegt.
- Läuft im bestehenden Python-Dienst ohne Root-Rechte. `mason` ist in den Gruppen `spi` und `gpio`.

## Entscheidung

**Option A: RSSI-Abtastung per SPI mit 1 kHz.** Der CC1101 wird einmalig für reinen Empfang konfiguriert (asynchroner Seriell-Modus ohne Datenausgang, FIFO ungenutzt) und in RX geschaltet. Ein Thread liest das RSSI-Statusregister im Millisekundentakt. Ein Burst-Detektor mit adaptiver Rauschreferenz erzeugt daraus dieselben Ereignisse (`burst`, `pair`) wie der RTL-SDR-Detektor, mit `source = "cc1101"` und `rssi_dbm`.

Alle SPI-Zugriffe laufen über eine **Sicherheitsschicht (`SafeCC1101Bus`)**. Sie lässt nur eine feste Befehlsliste zu und lehnt alles andere vor dem Zugriff auf `spidev` ab.

## Betrachtete Optionen

### Option A: RSSI-Abtastung per SPI (gewählt)

| Dimension | Bewertung |
|---|---|
| Komplexität | Niedrig: nur SPI, ein Thread |
| Zeitauflösung | ca. 1 ms (Abtastzeitpunkte werden mitprotokolliert) |
| Rechenlast | gering, ca. 1000 SPI-Zugriffe/s mit je ca. 30 µs |
| Datenschutz | sehr gut: Es existieren nur Pegelwerte, kein demoduliertes Signal |
| Vertrautheit | hoch: gleiches Ereignismodell wie der RTL-SDR-Detektor |

**Vorteile:** Funktioniert allein mit den vier SPI-Leitungen. Liefert Pegel in dBm (vergleichbar mit SNR/Anstieg). Leicht ohne Hardware testbar (Fake-SPI).
**Nachteile:** Python-Planung kann einzelne Abtastungen verzögern (p99 ≪ 1 ms, Ausreißer möglich). Burstgrenzen ±1–2 ms genau statt µs.

### Option B: Carrier-Sense über GDO0 mit gpiod-Flanken

| Dimension | Bewertung |
|---|---|
| Komplexität | Mittel: GPIO-Anforderung, Schwellenkonfiguration (AGCCTRL) |
| Zeitauflösung | sehr gut: Kernel-Zeitstempel je Flanke |
| Rechenlast | minimal, ereignisgesteuert |
| Datenschutz | sehr gut: nur Träger an/aus |
| Vertrautheit | gering: Schwellen müssen am Objekt eingemessen werden |

**Vorteile:** Präzise Burstgrenzen, kaum CPU-Last.
**Nachteile:** Kein Pegelwert. Die Schwelle ist eine Registereinstellung, die vorab eingemessen werden muss. Ohne RSSI ist keine adaptive Rauschreferenz möglich.

### Option C: Asynchroner Seriell-Modus mit GDO0-Abtastung

| Dimension | Bewertung |
|---|---|
| Komplexität | Hoch: Abtastung im µs-Bereich aus Python unzuverlässig |
| Zeitauflösung | theoretisch Bitebene |
| Datenschutz | **unzulässig**: GDO0 würde den demodulierten Bitstrom ausgeben |

**Abgelehnt:** Verstößt gegen die Regel „keine Bitdaten“ und wäre aus Python ohnehin nicht zuverlässig abzutasten.

## Abwägung

A und B schließen sich nicht aus. A liefert alles Nötige (Dauer, Pegel, Paarabstand) mit der geringsten Komplexität und ohne Einmessen. B ist eine spätere Verfeinerung für präzisere Burstgrenzen. Deshalb wird GDO0 schon jetzt auf **Carrier-Sense (IOCFG0 = 0x0E)** konfiguriert, nicht auf den Datenausgang. GDO2 wird hochohmig geschaltet (IOCFG2 = 0x2E). C scheidet aus Datenschutzgründen aus.

## Konsequenzen

- 433-MHz-Bursts werden auch bei laufendem ADS-B erfasst. Der befristete RTL-SDR-Scan bleibt für I/Q-Analysen nötig.
- Pegel in dBm sind **unkalibriert** (Datenblatt-Offset 74 dB bei 433 MHz). Vergleichbar sind sie nur innerhalb des CC1101, nicht mit RTL-SDR-SNR.
- Ein falsch gewählter Mittenfrequenz-Offset oder eine falsche Quarztoleranz (±20 ppm ≈ ±8,7 kHz) wird durch die 101-kHz-Kanalbandbreite abgefangen. Das kostet etwas Empfindlichkeit gegenüber einem schmaleren Filter.
- Die Sicherheitsschicht muss bei jeder Erweiterung mitgeprüft werden. Neue Register oder Befehle sind nur über die Positivliste möglich.
- Später zu prüfen: Option B als Ergänzung, sowie die Frage, ob 1 kHz unter Last stabil bleibt (die Abtastlücken werden gezählt und im Status gemeldet).

2. [x] `hardware/cc1101_rx.py`: Registertabelle 433,9156 MHz / 2-FSK / 101,6 kHz Kanalbandbreite, RSSI-Umrechnung, Burst- und Paar-Detektor, Empfangsthread mit Abtastlücken-Zähler, Gerätesperre.

4. [x] CLI `keyrfmonitor cc1101 listen --seconds N`, Web-API `/api/cc1101/rx/start|stop|status`, Dashboard-Karte.
