# CC1101 – Anschluss und Nur-Empfang (Raspberry Pi 5)

**Stand KeyRFMonitor 0.2.0:** Vorbereitung und **ausschließlich passive SPI-Chiperkennung**. Der CC1101 ist noch **kein** betriebsfähiger RX-Backend, kein TX-Backend. Der vorhandene RTL-SDR-Empfang bleibt unverändert. Keine Sende- oder Replay-Funktion für echte Fahrzeugtelegramme.

## Anschluss – SPI1 / CE0 (empfohlen bei Pironman-5-Gehäuse)

**SPI0 ist am Pi dieses Projekts belegt:** Das Pironman-5-Gehäuse steuert seine RGB-LEDs (WS2812) über `/dev/spidev0.0`, also SPI0-MOSI/GPIO10. Ein CC1101 an SPI0 würde jedes LED-Update als SPI-Verkehr empfangen. Deshalb SPI1 verwenden.

Vor dem Verkabeln Raspberry Pi ausschalten und von der Spannungsversorgung trennen.
Nur Module mit zur Pi-GPIO passenden **3,3-V-Pegeln** verwenden. Pinbezeichnungen können je nach CC1101-Trägerplatine abweichen.

| CC1101-Modulpin | Raspberry Pi 5 (BCM) | Physischer Pi-Pin |
|---|---|---:|
| VCC / VDD | 3V3 | 17 (oder 1) |
| GND | Masse | 39 (oder 6, 9, 14, …) |
| SCLK | SPI1 SCLK / GPIO21 | 40 |
| SI / MOSI | SPI1 MOSI / GPIO20 | 38 |
| SO / MISO | SPI1 MISO / GPIO19 | 35 |
| CSn / NSS | SPI1 CE0 / GPIO18 | 12 |
| GDO0 | GPIO25 (vorbereitet, optional) | 22 |
| GDO2 | GPIO24 (vorbereitet, optional) | 18 |

SPI1 aktivieren: in `/boot/firmware/config.txt` die Zeile `dtoverlay=spi1-1cs` ergänzen, neu starten, danach muss `/dev/spidev1.0` existieren. Die Pironman-5-Lüfter (GPIO5/6) kollidieren nicht.

Ohne Pironman-5-RGB (oder mit `rgb_enable: false`) ist alternativ SPI0/CE0 möglich: SCLK Pin 23, MOSI Pin 19, MISO Pin 21, CSn Pin 24; dann `--bus 0` (bei aktivem RGB zusätzlich `--allow-spi0`).

- **Nie 5 V an VCC oder GPIO des CC1101 anschließen** (sofern keine abweichende, eindeutig dokumentierte Trägerplatine mit eigenem Pegelwandler genutzt wird).
- GDO0 und GDO2 sind für die reine SPI-Chiperkennung nicht erforderlich; sie bleiben in dieser Version unbenutzt. Der Pi setzt keine GPIO-Ausgangsrichtung.
- Keine Last und keinen Sender ohne geeignete Antenne bzw. definierte, zulässige Labor-HF-Ankopplung betreiben.
- Vor der Verdrahtung mit `pinctrl get 16-21` prüfen, ob die vorgesehenen GPIOs frei sind.

## SPI vorbereiten – erst wenn das Modul vorhanden ist

```bash
echo 'dtoverlay=spi1-1cs' | sudo tee -a /boot/firmware/config.txt
sudo apt install -y python3-spidev
sudo reboot
ls -l /dev/spidev1.0
```

Gegebenenfalls Raspberry Pi neu starten, wenn die SPI-Schnittstelle anschließend nicht erscheint. Die erforderlichen Berechtigungen auf `/dev/spidev1.0` werden vom Betriebssystem verwaltet; es ist kein Betrieb des kompletten Monitors als Root vorgesehen.

Das **System-Python** verwenden. In deiner Shell zeigt `python3` derzeit auf die PlatformIO-Umgebung, die unter Umständen keine Debian-Pakete importiert.

```bash
cd ~/Projekte/MB-RF-Scan
/usr/bin/python3 -m keyrfmonitor cc1101 wiring
/usr/bin/python3 -m keyrfmonitor cc1101 probe
```

Standard des CLI ist SPI-Bus 1, CE0 (entspricht `--bus 1 --device 0`). Fehlt `/dev/spidev1.0`, nennt die Fehlermeldung das nötige Overlay. `--bus 0` wird abgelehnt, solange `/opt/pironman5/config.json` die RGB-LEDs aktiviert (`--allow-spi0` übersteuert das bewusst).

Die `probe`-Funktion nutzt SPI-Mode 0 bei maximal 500 kHz und sendet einen Weck-Strobe `SNOP` (0x3D, ohne Wirkung auf den Funkteil) und danach die zwei **SPI-Statusregister-Leseanforderungen** `0xF0` (PARTNUM) und `0xF1` (VERSION). Das sind SPI-Befehle, **keine HF-Aussendungen**. Sie startet keinen RX-/TX-Modus, schreibt keine CC1101-Konfigurationsregister und betätigt außer SNOP keine Strobes. Statusregisterantworten sind eine Plausibilitätsprüfung, kein Beleg für ein funktionierendes RF-Frontend. `PARTNUM=0x00` zusammen mit einer nicht trivialen Versionsantwort ist ein möglicher Hinweis auf einen CC1101; bei Klonen können IDs abweichen.

Beispiel einer möglichen **simulierten** Ausgabe (nicht an deinem Pi gemessen):

```json
{
  "partnum": "0x00",
  "version": "0x14",
  "cc1101_plausible": true,
  "rx_implemented": false,
  "tx_implemented": false
}
```

## Nur-Empfang (ab v0.10.0)

```bash
cd ~/Projekte/MB-RF-Scan
/usr/bin/python3 -m keyrfmonitor cc1101 listen --seconds 60
```

Oder im Dashboard: Karte **CC1101-Empfang** → *CC1101-Empfang starten*. Der Empfang läuft parallel zu ADS-B. Er tastet nur den Empfangspegel (RSSI) mit 1 kHz ab und speichert Burst-/Paar-Metadaten mit `source = cc1101`. Bits, Rahmen oder Schlüsseldaten werden nicht erzeugt. Pegel sind unkalibriert (Datenblatt-Offset 74 dB).

Jeder SPI-Zugriff läuft über `SafeCC1101Bus` (`keyrfmonitor/hardware/cc1101_bus.py`), der nur eine feste Positivliste zulässt. Senden (STX), TX-FIFO und Ausgangsleistung (PATABLE ≠ 0x00) sind technisch ausgeschlossen. Hintergrund und Alternativen: [ADR-0001](adr/0001-cc1101-rx-only.md).

## Grenzen, Entwicklungsstrategie

1. **Jetzt:** CC1101-Projektstruktur, Anschlussbelegung, CLI-Diagnose und Test-Doubles. Weder USB-RTL-SDR noch `dump1090.service` werden durch die CC1101-Diagnose verändert.
2. **Nach Anschluss:** Plausible Registerantwort und elektrische Verbindungen bestätigen. Erst danach kann ein RX-only-Treiber als separat testbare Komponente aufgebaut werden.
3. **Später optional:** Eigene synthetische Labor-Testtelegramme können in einem **gesonderten, abgeschirmten, regelkonformen HF-Testaufbau** untersucht werden. Gegenwärtig ist ausdrücklich kein physischer Sender integriert.

**Keine IQ-/Schlüsseldaten** des Mercedes werden an den CC1101-Treiber übergeben. Die Software trennt die passive Fahrzeug-Funkdiagnose von den bereits vorhandenen virtuellen, synthetischen Testvektoren.
