# CC1101 – Hardwarevorbereitung (Raspberry Pi 5)

**Stand KeyRFMonitor 0.2.0:** Vorbereitung und **ausschließlich passive SPI-Chiperkennung**. Der CC1101 ist noch **kein** betriebsfähiger RX-Backend, kein TX-Backend. Der vorhandene RTL-SDR-Empfang bleibt unverändert. Keine Sende- oder Replay-Funktion für echte Fahrzeugtelegramme.

## Anschluss – SPI0 / CE0

Vor dem Verkabeln Raspberry Pi ausschalten und von der Spannungsversorgung trennen.
Nur Module mit zur Pi-GPIO passenden **3,3-V-Pegeln** verwenden. Pinbezeichnungen können je nach CC1101-Trägerplatine abweichen.

| CC1101-Modulpin | Raspberry Pi 5 (BCM) | Physischer Pi-Pin |
|---|---|---:|
| VCC / VDD | 3V3 | 1 |
| GND | Masse | 6 |
| SCLK | SPI0 SCLK / GPIO11 | 23 |
| SI / MOSI | SPI0 MOSI / GPIO10 | 19 |
| SO / MISO | SPI0 MISO / GPIO9 | 21 |
| CSn / NSS | SPI0 CE0 / GPIO8 | 24 |
| GDO0 | GPIO25 (vorbereitet, optional) | 22 |
| GDO2 | GPIO24 (vorbereitet, optional) | 18 |

- **Nie 5 V an VCC oder GPIO des CC1101 anschließen** (sofern keine abweichende, eindeutig dokumentierte Trägerplatine mit eigenem Pegelwandler genutzt wird).
- GDO0 und GDO2 sind für die reine SPI-Chiperkennung nicht erforderlich; sie bleiben in dieser Version unbenutzt. Der Pi setzt keine GPIO-Ausgangsrichtung.
- Keine Last und keinen Sender ohne geeignete Antenne bzw. definierte, zulässige Labor-HF-Ankopplung betreiben.
- Vor der Verdrahtung prüfen, ob SPI0 und die vorgesehenen GPIOs nicht bereits von anderer Hardware beansprucht werden.

## SPI vorbereiten – erst wenn das Modul vorhanden ist

```bash
sudo raspi-config nonint do_spi 0
sudo apt install -y python3-spidev
ls -l /dev/spidev0.0
```

Gegebenenfalls Raspberry Pi neu starten, wenn die SPI-Schnittstelle anschließend nicht erscheint. Die erforderlichen Berechtigungen auf `/dev/spidev0.0` werden vom Betriebssystem verwaltet; es ist kein Betrieb des kompletten Monitors als Root vorgesehen.

Das **System-Python** verwenden. In deiner Shell zeigt `python3` derzeit auf die PlatformIO-Umgebung, die unter Umständen keine Debian-Pakete importiert.

```bash
cd ~/Projekte/KeyRFMonitor
/usr/bin/python3 -m keyrfmonitor cc1101 wiring
/usr/bin/python3 -m keyrfmonitor cc1101 probe
```

Alternativ bei CE1 (nur bei entsprechend anderer Verdrahtung): `--device 1`. Standard ist SPI-Bus 0, CE0.

Die `probe`-Funktion nutzt SPI-Mode 0 bei maximal 500 kHz und sendet ausschließlich die zwei **SPI-Statusregister-Leseanforderungen** `0xF0` (PARTNUM) und `0xF1` (VERSION). Das sind SPI-Befehle, **keine HF-Aussendungen**. Sie startet keinen RX-/TX-Modus, schreibt keine CC1101-Konfigurationsregister und betätigt keine Strobes. Statusregisterantworten sind eine Plausibilitätsprüfung, kein Beleg für ein funktionierendes RF-Frontend. `PARTNUM=0x00` zusammen mit einer nicht trivialen Versionsantwort ist ein möglicher Hinweis auf einen CC1101; bei Klonen können IDs abweichen.

Beispiel einer möglichen **simulierten** Ausgabe (nicht an deinem Pi gemessen):

```json
{
  "partnum": "0x00",
  "version": "0x14",
  "cc1101_plausible": true,
  "rx_implemented": false,
  "tx_implemented": false
}
```

## Grenzen, Entwicklungsstrategie

1. **Jetzt:** CC1101-Projektstruktur, Anschlussbelegung, CLI-Diagnose und Test-Doubles. Weder USB-RTL-SDR noch `dump1090.service` werden durch die CC1101-Diagnose verändert.
2. **Nach Anschluss:** Plausible Registerantwort und elektrische Verbindungen bestätigen. Erst danach kann ein RX-only-Treiber als separat testbare Komponente aufgebaut werden.
3. **Später optional:** Eigene synthetische Labor-Testtelegramme können in einem **gesonderten, abgeschirmten, regelkonformen HF-Testaufbau** untersucht werden. Gegenwärtig ist ausdrücklich kein physischer Sender integriert.

**Keine IQ-/Schlüsseldaten** des Mercedes werden an den CC1101-Treiber übergeben. Die Software trennt die passive Fahrzeug-Funkdiagnose von den bereits vorhandenen virtuellen, synthetischen Testvektoren.
